# App CTA: client-side store branching, no deep-link service

The App CTA (`features/app-install/app-cta-button.tsx`) sends users to the app
store with **no deep-link redirect service** (OneLink/Branch). A pure function,
`resolveStoreUrl(userAgent, maxTouchPoints)` in `lib/store-link`, reads the
device from the User-Agent and returns the matching store URL from the single
link constant in `content/cta.ts`:

- **Android** → Play Store.
- **iOS** (incl. iPadOS 13+, which masquerades as a Mac UA — disambiguated by
  `maxTouchPoints > 1`) → App Store.
- **Desktop / anything unclassifiable** → Play Store (fallback).

This overrides issue #10's original plan (a OneLink/Branch link that branches
server-side and carries deferred deep-link context). The CTA renders only on
**Result** — the glossary's earlier "Intro and Result" was aspirational; intro
never rendered the button, and this decision makes Result-only canonical.

## Resolution mechanics

The button is a `'use client'` anchor, but a client component still SSRs, and the
server can't know the device. `storeUrl` is seeded with the desktop fallback
(`resolveStoreUrl('')` → Play) so server and first client render agree — no
hydration mismatch — then a mount effect corrects it to
`resolveStoreUrl(navigator.userAgent, navigator.maxTouchPoints)`. Keeping a real
`href` (not a click-time `window.open`) preserves right-click / long-press /
screen-reader link semantics.

## Attribution

No service means no unified attribution; we recover the cheap half on the store
URLs themselves and accept the rest as a gap:

- **Play**: a `referrer=utm_source%3Dparrot_mbti%26utm_medium%3Dapp_cta` param,
  read app-side via the Play Install Referrer API. Zero web-side cost.
- **App Store**: an App Store Connect campaign link (`?pt=…&ct=…&mt=8`, on the
  `/app/apple-store/` path). Apple requires **both** `pt` (provider token) and
  `ct`, generated by creating a campaign in App Store Connect — it is account
  work, not a URL a param can fake. Issued and wired in `content/cta.ts`
  (`pt=129074287`, `ct=buddybird-mbti-web`).
- **Clicks** keep flowing through GA4 `app_cta_click` (placement=result).

## Considered Options

- **Client-side UA branching (chosen)** — no third-party account, no SDK, no cost;
  a single pure function + one constant, swappable for a service later via the
  same constant. Limitation: no deferred deep link, and install attribution is
  per-store and coarse.
- **OneLink/Branch deep-link service (issue #10 original)** — one link branches
  server-side, unified attribution, passes post-install context. Costs an account,
  setup, and a human decision (why it sat `ready-for-human`); heavier than a
  viral MVP that just needs to land people on the right store page.
- **Server-side UA redirect (Next route handler)** — no client flicker, but adds a
  dynamic endpoint to an otherwise static export (against ADR-0002's standalone
  posture) for a branch two regexes handle on the client.

## Consequences

- **Reversible via one constant.** Adopting a deep-link service later means
  pointing both `APP_STORE_URL`/`PLAY_STORE_URL` (or a single resolved URL) at the
  service link — `resolveStoreUrl` and the button are untouched.
- **iPad correctness costs `maxTouchPoints`.** Without it, iPadOS users fall to the
  Play fallback; the touch-point check keeps them on the App Store.
- **The attribution gap is explicit.** iOS installs don't attribute until the
  campaign link is issued; cross-store unified funnel numbers never exist. Read
  clicks from GA4, installs from each store console separately.
- **E2E unaffected.** `e2e/flows/funnel-events.mjs` asserts on the `app-cta-result`
  testid and the `app_cta_click` event, both unchanged; the resolved `href` value
  is not asserted.
- **No unit test harness exists** (units rely on `tsc` + eslint + e2e). The
  branching is left transparent rather than adding a runner; if one lands,
  `resolveStoreUrl` is a pure function ready to test.
